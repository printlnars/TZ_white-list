# Извлечение данных из документов (тестовое задание A — LLM Engineer)

CLI получает текст документа (счёт, КП, акт) и возвращает JSON по схеме из ТЗ.
Основная задача — **модель не должна выдумывать то, чего нет в документе**. Поэтому
ответ LLM проходит строгую валидацию схемы, а затем детерминированные гардрейлы
сверяют каждое поле с исходным текстом.

```
текст ──► LLM (structured output по JSON Schema)
            │
            ▼
       парсинг JSON + строгая pydantic-валидация ──✗──► ошибки отправляются модели, повтор (до 3 попыток)
            │ ✓                                              │ 3 раза ✗
            ▼                                                ▼
       гардрейлы: сверка каждого поля с текстом       всё null + VALIDATION_FAILED, exit code 2
       (обнулить выдуманное, разрешить противоречия,        (документ уходит на ручную разметку)
        посчитать field_confidence, warnings)
            │
            ▼
       финальная pydantic-валидация ──► JSON
```

## Запуск с нуля

Нужны Python ≥ 3.10, `git` и `make`. Ключи API и GPU **не нужны** (по умолчанию работает офлайн-мок, см. ниже).

```bash
git clone https://github.com/printlnars/TZ_white-list.git docextract
cd docextract
make eval     # создаёт .venv, ставит зависимости (pydantic, pytest), прогоняет eval по всему набору
make test     # 35 юнит-тестов
```

Без `make` — то же самое вручную:

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python eval.py                    # отчёт eval (бэкенд rules)
.venv/bin/python eval.py --backend greedy   # мок «самоуверенной» LLM: видно, что ловят гардрейлы
.venv/bin/python -m pytest -q               # тесты
```

Разобрать один документ:

```bash
.venv/bin/python -m docextract dataset/03_given_kz_ocr.txt
.venv/bin/python -m docextract dataset/03_given_kz_ocr.txt --debug   # в stderr: попытки, ошибки валидации, ответ модели до гардрейлов
cat my_doc.txt | .venv/bin/python -m docextract -                     # из stdin
```

Код выхода: `0` — успех, `2` — модель так и не выдала валидный JSON.

## Бэкенды LLM и как решён вопрос с доступом к API

Платного ключа у меня нет, на машине разработки нет и Ollama, поэтому сделано так:

| `--backend` | Что это | Переменные окружения |
|---|---|---|
| `rules` (по умолчанию) | **Мок LLM**: детерминированный эвристический экстрактор ([rules.py](docextract/rules.py)) за тем же интерфейсом, что и модель. Возвращает сырую JSON-строку, которая дальше проходит тот же путь: парсинг → валидация → гардрейлы. | — |
| `greedy` | **Мок «самоуверенной» LLM**: ответ `rules` плюс типичные галлюцинации, которые запрещает ТЗ: сегодняшняя дата вместо отсутствующей, НДС посчитан сам (16/116), БИН «выведен» из названия, итог сложен из позиций, валюта KZT «по умолчанию». Нужен, чтобы показать на eval, что ловят гардрейлы. | — |
| `ollama` | Локальная модель через Ollama `/api/chat`, `format` = JSON Schema (constrained decoding), `temperature=0`. | `OLLAMA_MODEL` (по умолч. `qwen2.5:7b`), `OLLAMA_HOST` (по умолч. `http://localhost:11434`) |
| `openai` | Любой OpenAI-совместимый API (OpenAI, vLLM, LM Studio, OpenRouter…). | `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` |

Пайплайн, валидация, ретраи, гардрейлы и eval — настоящие и одинаковые для всех бэкендов.
HTTP-клиенты проверены тестами на локальном фейковом сервере ([tests/test_llm_clients.py](tests/test_llm_clients.py)).

Запуск на настоящей модели:

```bash
# установить Ollama: https://ollama.com/download
ollama pull qwen2.5:7b
make eval BACKEND=ollama               # или: OLLAMA_MODEL=qwen2.5:3b make eval BACKEND=ollama
```

## Что делает система, если ответ не прошёл валидацию

Схемы — [docextract/schema.py](docextract/schema.py), pydantic в strict-режиме:
лишние поля запрещены; `"160 500"` строкой вместо числа — ошибка (без тихого приведения типов);
`supplier_bin` — ровно 12 цифр; `doc_date` — `YYYY-MM-DD` и реальная дата (`2026-02-30` отклоняется);
`doc_type`/`currency` — только значения из перечня; суммы ≥ 0.

1. Не JSON или не прошло схему → текст ошибок (`supplier_bin: String should match pattern '^\d{12}$'`)
   отправляется модели в том же диалоге с просьбой исправить.
2. До 3 попыток.
3. Если все 3 неудачны — возвращается безопасный результат: `doc_type: "unknown"`, все поля `null`,
   в `warnings` — `VALIDATION_FAILED` с последними ошибками; CLI завершается с кодом 2.
   Невалидные данные дальше по системе не идут.
4. Выход самих гардрейлов тоже валидируется схемой `Extraction` — ошибка в гардрейлах даст исключение, а не тихий мусор.

Это покрыто тестами: `test_retry_*`, `test_fallback_when_model_never_returns_valid_json`.

## Гардрейлы: правила и решения по неоднозначностям

Гардрейлы ([guardrails.py](docextract/guardrails.py)) **никогда не придумывают значения**. Они могут только
(а) обнулить поле, которого нет в тексте, (б) выбрать одно из значений, буквально присутствующих в тексте,
по правилу ниже, (в) добавить предупреждение. Текст перед сверкой проходит OCR-нормализацию
(`l/I/O` → `1/0` в числовых токенах, `0` → `о` и латиница-двойник → кириллица в словах).

| Поле | Правило |
|---|---|
| `supplier_bin` | 12-значное число должно быть в тексте (после OCR-нормализации). Если оно в блоке «Покупатель/Заказчик/Тапсырыс беруші» → `null` + `BIN_IS_BUYER`. Если найдено только после исправления OCR → оставляем + `BIN_OCR_CORRECTED`, уверенность 0.7. Не проходит контрольную сумму БИН РК → **оставляем** (оно есть в документе), но `BIN_CHECKSUM_INVALID` и уверенность 0.5. |
| `supplier_name` | Продавец/поставщик/исполнитель, не покупатель. Должно находиться в тексте (сравнение без учёта регистра, кавычек, ОПФ, казахских букв). Двуязычное название (`ЖШС «Көкжиек Құрылыс» / ТОО "Кокжиек Курылыс"`) — принимается любой вариант. |
| `doc_number` | Должен стоять в тексте рядом с `№ / No / N° / номер` или в шапке (первые 3 строки). Номер договора-основания — не номер документа. |
| `doc_date` | **Дата составления документа.** Сроки оплаты/действия («до», «действителен», «оплатить», «дейін», «valid until») и даты договоров-оснований — не дата документа. Если модель вернула такую дату → заменяем на дату документа из текста (`DOC_DATE_OVERRIDDEN`) или `null`, если её нет. **Если дат документа несколько и они разные → `DATE_CONFLICT` и берём первую по тексту (из шапки, рядом с номером)**: шапку формирует учётная система, ниже — обычно ручные правки. |
| `currency` | Только при явном указании (тенге/тг/₸/теңге/тиын, USD/$, EUR/€). «Документ казахстанский — значит KZT» не допускается. |
| `total_amount` | **Итог к оплате, с НДС, если НДС указан.** Должен быть в тексте цифрами или прописью (рус/каз) в строке «итого / всего / к оплате / жалпы / барлығы / total». Промежуточные итоги («без НДС» или X, где X + НДС = другой итог) — не итог; если модель вернула подытог → заменяем на итог (`TOTAL_OVERRIDDEN`). Сумму позиций **не** складываем сами: нет строки с итогом — `null`. **Если в документе несколько разных итогов → `TOTAL_CONFLICT`; выбираем:** (1) сходящийся с суммой позиций (с НДС или без); иначе (2) записанный прописью (юридический приоритет суммы прописью); иначе (3) последний по тексту. |
| `vat_amount` | Только сумма, написанная в строке с НДС/ҚҚС/VAT (числа из процентов и дат не считаются). Не вычисляем. «НДС не облагается»/«без НДС» → `null` + `VAT_NOT_APPLICABLE` (не 0: нуля в документе нет). «Цены с НДС» без суммы → `null`. |
| `line_items` | Позиция удаляется, если её названия нет в тексте; `qty`/`price` обнуляются, если таких чисел нет в тексте. `price` — цена за единицу; если указана только сумма строки без количества — `qty: null`. |
| `doc_type` | `Шот-фактура`/`счёт-фактура` → `invoice`. Документы вне перечня (накладная, договор) → `unknown`, остальные поля всё равно заполняются, если они есть. |
| арифметика | Сумма позиций (qty×price) не сходится с итогом (ни с НДС, ни без) → `ARITHMETIC_MISMATCH`, уверенность итога снижается. |

**`field_confidence`** считается детерминированно (самооценке LLM не доверяем): ключи — все скалярные поля и `line_items`;
`0.0` — поле `null` (ничего не утверждаем); `0.9–0.95` — значение найдено в тексте как есть; `0.7` — найдено после
OCR-исправления; `0.6` — значение выбрано правилом при противоречии; `0.5` — слабое подтверждение (БИН с неверной
контрольной суммой, тип документа без ключевых слов).

**`warnings`** — строки вида `КОД: пояснение`. Коды: `UNGROUNDED`, `BIN_IS_BUYER`, `BIN_OCR_CORRECTED`,
`BIN_CHECKSUM_INVALID`, `SUPPLIER_IS_BUYER`, `DOC_NUMBER_IS_CONTRACT`, `DATE_CONFLICT`, `DOC_DATE_OVERRIDDEN`,
`DOC_DATE_NOT_ISSUE`, `CURRENCY_CONFLICT`, `TOTAL_CONFLICT`, `TOTAL_OVERRIDDEN`, `VAT_NOT_APPLICABLE`, `VAT_GE_TOTAL`,
`ARITHMETIC_MISMATCH`, `DOC_TYPE_WEAK`, `VALIDATION_FAILED`; предупреждения самой модели — с префиксом `LLM:`.

## Eval

`make eval` (или `python eval.py --backend …`) печатает по каждому полю: accuracy, **галлюцинации** (заполнено, в
эталоне `null`), **пропуски** (`null`, в эталоне значение) и неверные значения — раздельно. Всё считается дважды:
по ответу модели после валидации схемы, но **до гардрейлов**, и по финальному ответу. `doc_type: "unknown"`
считается аналогом `null`. Для `line_items` accuracy = весь список совпал; лишние позиции — галлюцинации,
ненайденные — пропуски. Полный отчёт сохраняется в `reports/eval_<backend>.json`.

Результаты на момент сдачи:

**`greedy`** (мок с типичными галлюцинациями LLM) — показывает работу гардрейлов:

```
field           accuracy  halluc.  omiss.  wrong   | до гардрейлов: acc / halluc / omiss
supplier_bin        100%        0       0      0   |   77% /   3 /   0
doc_number          100%        0       0      0   |   77% /   3 /   0
doc_date            100%        0       0      0   |   92% /   1 /   0
currency            100%        0       0      0   |   85% /   2 /   0
total_amount        100%        0       0      0   |   85% /   1 /   0
vat_amount          100%        0       0      0   |   54% /   6 /   0
line_items          100%        0       0      0   |   92% /   2 /   0
ГАЛЛЮЦИНАЦИИ: 0   (до гардрейлов: 18)
ПРОПУСКИ:     0   (до гардрейлов: 0)
```

**`rules`**: 100% по всем полям, 0 галлюцинаций, 0 пропусков, 8/8 ожидаемых предупреждений; до гардрейлов была 1
неверная сумма (в документе 06 мок взял итог прописью, гардрейл разрешил противоречие по правилу).
**Эту цифру нельзя считать качеством решения**: эвристики и документы писал один человек, это переобучение
на 13 примерах. Ценность этого прогона — в том, что весь пайплайн и eval работают офлайн, а прогоны на наборе
поймали 3 реальных бага гардрейлов (см. историю коммитов и REFLECTION.md).

**`ollama`**: не прогонялся — на машине разработки нет Ollama/GPU-окружения. Команда выше.

## Что сделано и что нет

Сделано:
- CLI + строгая схема (pydantic strict), ретрай с передачей ошибок модели, безопасный фолбэк, код выхода.
- Гардрейлы против галлюцинаций: сверка каждого поля с текстом, OCR-нормализация, суммы прописью (рус/каз),
  даты (рус/каз/англ), контрольная сумма БИН, роли «поставщик/покупатель», разрешение противоречий по правилам.
- Детерминированный `field_confidence`.
- Бэкенды Ollama и OpenAI-compatible, два мока.
- 13 документов с эталонами, eval с раздельным учётом галлюцинаций/пропусков до и после гардрейлов.
- 35 тестов.

Не сделано / ограничения:
- **Не прогнан eval на настоящей LLM** — главная дыра. Неизвестно, как часто реальная модель ошибается
  (особенно 3–7B на казахском тексте) и сколько ретраев нужно.
- Проверка «значение есть в тексте» — по всему документу, а не по конкретному месту: если выдуманное число
  случайно встречается в другом месте документа, гардрейл его пропустит (`100` найдётся внутри `2 100`).
- Ключевые слова итогов/ролей — словари; документ с непривычной формулировкой даст пропуск (сознательный выбор:
  пропуск дешевле галлюцинации).
- Набор из 13 документов мал, у эталонов один разметчик.

Что дальше (по приоритету):
1. Прогнать `ollama` (qwen2.5 7B/14B, llama 3.1 8B) и API-модели, сравнить галлюцинации до/после гардрейлов.
2. Просить у модели цитату-обоснование для каждого поля (`evidence`) и сверять значение с цитатой, а не со всем текстом.
3. Отложенная выборка из реальных документов клиента, двойная разметка эталонов.
4. HTTP-сервис (FastAPI) поверх `pipeline.extract`, очередь ручной проверки для полей с уверенностью < 0.7.

```

  schema.py      pydantic-схемы LLMOutput (ответ модели) и Extraction (ответ сервиса)

  llm.py         бэкенды: Ollama, OpenAI-compatible, моки rules/greedy, ScriptedLLM для тестов
  pipeline.py    LLM -> парсинг -> валидация -> ретрай/фолбэк -> гардрейлы

  __main__.py    CLI

tests/           pytest
REFLECTION.md    ответы на вопросы и вопрос на архитектуру
```
